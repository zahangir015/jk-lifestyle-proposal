01

Board decision

Approve an architecture-led program, not a collection of disconnected applications.

The proposal uses shared identity and controlled domain ownership so Website, App, ERP, Clinical and future AI capabilities can grow without creating another fragmented technology estate.

Architecture styleModular monolith / bounded domains

5–6 domain-aligned deployable services with clean internal contracts. Microservices are introduced only when scaling, compliance or workload isolation justifies them.

ERP strategyStaged transition: Odoo CE first, JK platform long term

Boundary rule

No direct access to another module's database

Each business module owns its data. Other modules communicate through controlled system interfaces or business events instead of reading each other's database tables directly.

Evolution rule

Modular now, extract later

Clinical and AI/Food Recognition are the likely first candidates for independent services if workload isolation or compliance requirements increase.

Data rule

Events captured from day one

Operational events needed for alerts, analytics and future prediction are written once and consumed by multiple downstream capabilities.

Migration rule

Parallel run before cutover

No major system changes directly against live business operations without rehearsal, reconciliation, rollback and business-owner sign-off.

05

Integration, sync & real-time

Design for intermittent connectivity, event-driven updates and controlled external dependencies.

Retail, clinical and device workflows cannot depend on perfect internet connectivity or tightly coupled vendor APIs.

POS & Inventory transition

Use Odoo CE quickly, then replace it with JK-built modules

  1. Clean the existing Excel product, outlet and stock data before importing it into Odoo Community Edition.
  2. Use Odoo POS and Inventory for the first live outlet operations so the business does not wait for the full custom build.
  3. Build the JK Inventory and POS modules in parallel, using the real Odoo/Excel data and business rules as the reference.
  4. Run both systems side by side and compare sales, payments, stock movements, returns and closing balances.
  5. Move outlets one by one only after the new system passes user acceptance testing and reconciliation. After cut-over, the JK system becomes the operational source of truth.
Wearables / continuous glucose monitor

Broad platform integrations first

  1. Health Connect and HealthKit are the default ingestion hubs.
  2. A direct vendor system interface or Bluetooth connection is used only when the device is not supported by the main health platforms.
  3. Manual entry remains available for every metric and uses the same backend endpoint.
  4. Near-real-time push is preferred; otherwise scheduled polling can match device cadence.
  5. Duplicate readings use source/time conflict rules; manual entries fill genuine data gaps.
Event backboneRabbitMQ first

Operational events feed multiple consumers without duplicating write paths. Kafka is deferred until event volume clearly justifies the operational overhead.

NotificationsDomain-event triggered

FCM/APNs for mobile push; WebSocket for outpatient queue and live manager dashboards. Avoid polling where event-driven delivery is available.

Reliability controlsIdempotency + trace IDs

Offline sync and integrations require repeat-safe processing, correlation IDs and observable retry behavior during network or vendor failure.

Community feedHybrid consistency

User writes are immediately consistent; ranked-feed calculations happen asynchronously to avoid premature real-time ranking complexity.

06

Security, privacy & resilience

Security controls are architecture components, not release-time add-ons.

Health data, finance data and identity receive stricter controls than ordinary application content.

01

Role-based access control

Permissions are controlled by business concern, location and job function. The rules are enforced by the central integration layer and backend services, not only by hiding screens in the user interface.

02

Strong login security

Staff and administrators use two-step verification. Customers and patients can use a one-time-password login to keep onboarding simple while protecting access.

03

Encryption + health-data isolation

Encryption in transit and at rest, plus field-level encryption for sensitive patient medical records, device and care-plan fields.

04

Read and write auditability

Sensitive health-data access is logged on reads as well as writes, enabling traceable access review.

05

Consent as data

Consent is stored as an explicit, revocable record that governs community sharing, device data and analytics/AI use.

06

Continuous application security

The automated build process checks third-party libraries and source code for common security problems. Independent security testing is required before major production releases.

Backup and disaster recoveryAutomated backups are tested regularly. Each important module has a defined recovery-time target and an acceptable data-loss limit, and the recovery process is rehearsed before major releases.
Outlet continuityDuring the Odoo phase, we will test the selected Odoo CE offline and reconnect behavior. The JK-built POS will later include a tested offline mode and safe background synchronization.
System monitoringLogs, request tracking, performance metrics, agreed service targets, security issues and monthly cloud-cost reviews will be visible in one monitoring view.

Q

Concise board answers

Four high-impact questions, answered in operational terms.

These answers summarize controls already defined across architecture, delivery, risk management and operating-cost design.

Q10 · Project failure Three primary failure drivers to control

Dirty Excel or Odoo data can cause stock and reporting errors, so data must be cleaned early, migrated in stages and reconciled before cut-over. Changing clinical workflows can cause rework, so clinical experts should review prototypes and approve the workflow before development is finalized. Team-capacity or scope pressure should be controlled through phased hiring, clear acceptance criteria, formal change control and quarterly delivery gates.

Q14 · Community moderation Automation flags; humans decide

Technology auto-flags health-misinformation patterns, while humans make moderation decisions through a Moderation Console within a defined review time. Moderation tooling and minimum moderation capacity are hard Community go-live gates; health-content decisions are not delegated to AI alone.

Q15 · Dangerous alerts Clinician accountability with reliable escalation

A dangerous reading triggers the Alert Engine, which notifies the patient and creates the assigned clinician task in parallel. The clinician is accountable within a defined response time; unacknowledged alerts escalate to the on-call supervisor. Queued events, safe retries that do not create duplicate actions, delivery monitoring, request tracking IDs and a full audit trail protect reliability.

Q16 · Media & AI cost Control variable cost at every layer

Right-size compute with autoscaling limits; compress images, use Content Delivery Network caching, adaptive-bitrate video and lifecycle/cold-storage rules; cache repeated/common meal recognition and batch non-urgent AI processing. Track storage, content-delivery and AI unit costs monthly and move from Buy to Build only when quality and economics justify it.

Risk controls

Architecture and budget controls are designed around the program's highest exposures.

The highest risks are hiring, dirty operational data, clinical workflow churn, scope expansion and security/compliance defects.

If Year-1 budget is constrained

Defer optional growth capabilities before weakening the foundation.

Defer first
  • Community platform and online education platform.
  • Advanced wearable and continuous-glucose-monitor integration.
  • Building the food-recognition model in-house.
  • Franchise and Health Tourism/Sinbad integrations.
Protect
  • JK ID / single sign-on, API Gateway and clean master data.
  • Core security controls.
  • Odoo CE transition for current outlet POS and Inventory operations.
